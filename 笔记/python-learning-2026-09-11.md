# 第一部分：线程与 GIL（第 1 关）

## 一、程序的两种"忙"（本域地基）

| | 像什么 | 忙在哪 | 例子 |
|---|---|---|---|
| **IO 密集** | **点外卖** | 在**等**（小哥在路上） | 调 API、爬虫、读写文件 |
| **CPU 密集** | **自己做饭** | 在**算**（全程站灶台） | 大数求和、图像处理 |

- IO = Input/Output，指程序与外部世界打交道（网络/磁盘/数据库）
- 点外卖时你在等，等的时候可以同时点三家 = 并发的价值
- 做饭必须站灶台前，没法同时炒三道菜 = 要多个厨房（多进程，第 2 关）

**用户报考的 AI 应用开发几乎全是 IO 密集** —— 程序 90% 时间在等大模型返回。

---

## 二、GIL（全局解释器锁）—— 本域的核心

**一句话：CPython 解释器里，同一时刻只允许一个线程执行 Python 字节码。**

> 类比：一个办公室（进程）里有好几个员工（线程），但**只有一支笔**（GIL）。谁拿到笔谁才能写字。

- **为什么有它**：早期为了让内存管理（引用计数）简单安全，不用给每个对象加锁。性能换简单。
- Python 3.13+ 有实验性「无 GIL」构建，但默认版本仍然有。

### 关键机制：换笔的时机是"在段落之间"

线程不是想换就换，而是跑到**特定安全点**才会被换掉。这解释了一切：

| 操作类型 | 换笔行为 | 结果 |
|---|---|---|
| `time.sleep` / 网络请求 | 线程**主动举手**"我在等人，笔给你" | 换笔立刻发生，另一个线程接手 → **等待重叠** |
| `counter += 1` 这类极短操作 | 读-改-写三条指令挨着，**碰不到安全点** | 一个线程常能连着跑很多次才被换 |

### 一句话结论

> **GIL 挡的是"算"，不挡"等"。**
> 判断该不该用线程，问：**这活儿主要是在等，还是在算？**

## 三、跑出来的数据（实测）

### 题 1：串行 vs 并发（3 个任务，各等 0.5 秒）

```
串行耗时: 1.50 秒
并发耗时: 0.50 秒      ← 接近 3 倍提速（任务数就是天花板）
```

并发版打印顺序：`开始 A B C` → `完成 B` → `完成 A` → `完成 C`

**B 抢在 A 前面完成了 —— 谁先跑、谁先完成由操作系统调度决定，不是 bug，是并发的本性。**

### 题 2：GIL 实证（第 1 关的主角）

```
CPU 密集  串行: 0.29 秒   线程: 0.29 秒     ← 一点没快
IO  密集  串行: 1.00 秒   线程: 0.50 秒     ← 正好快一倍
```

同一套线程代码、同样的 start/join 写法，结果天差地别：

- **CPU 版**：两个线程都要笔，只能排队 → 等于没并发
- **IO 版**：一个等的时候主动交笔，另一个立刻接手 → 两份等待重叠

（进阶观察：计算量小所以抢笔开销没显出来。把 `range(2_000_000)` 改成 `range(20_000_000)`，线程版会**明显慢于**串行版。）

### 题 4：竞态条件实验（意外的教学金矿）

`broken()` 跑出 200000，**没丢数**。深挖后发现：

```
A. 自然写法 counter += 1         期望 200000  实际 200000  丢了 0
B. 中间插入 time.sleep(0)        期望 2000    实际 330     丢了 1670（83%）
```

（还试过 `sys.setswitchinterval(1e-6)` 把时间片调到 1 微秒，也没能让 A 丢数 —— **问题不在时间片长短，在于切换点根本落不进 `+=` 中间**。）

**核心教训：A 没出事是"碰巧"，不是"安全"。竞态条件的本质是偶发。**

## 四、线程三步走：造 → 跑 → 等

```python
t = threading.Thread(target=download, args=("A", 0.5))   # ① 造
t.start()                                                 # ② 跑
t.join()                                                   # ③ 等
```

| 步骤 | 干了什么 | 常见误解 |
|---|---|---|
| **造** | 只是**写了张任务卡**，函数一次都没执行 | 以为写了就跑 |
| **跑** | `start()` 把卡交给操作系统，真正开始 | 以为 join 才是"开始" |
| **等** | `join()` 让主线程**停在这等**它结束 | 以为 join 在"推进"线程 |

### 必须「先全 start，再全 join」

```python
# ✅ 并发：三个线程同时活着
for t in threads: t.start()
for t in threads: t.join()

# ❌ 语法没错，但退化成串行
for t in threads:
    t.start()
    t.join()      # 启动一个就等它完，等于排队
```

第二种**不报错、能跑通，只是慢 3 倍** —— 静默的错误，最难发现。

### `args=` 是"传参通道"

线程启动时会替你执行 `target(*args)`：

```python
args=(i,)        →  worker(*(i,))        →  worker(i)
args=(i, 0.5)    →  worker(*(i, 0.5))    →  worker(i, 0.5)
```

- 对应的还有 `kwargs=` 关键字通道
- **元组坑**：`args=(i)` 不是元组，括号只是普通括号！单元素必须写 `args=(i,)`
- 另有一条"绕路"：`lambda x=i: ...` 用**默认参数拍快照**把值焊死在函数上。能跑但不是正路（不写 `x=i` 就会踩闭包捕获"变量而非值"的坑）。**用 `args=(i,)`。**

## 五、两个实战坑

### 坑 1：线程的返回值，拿不到

```python
t = threading.Thread(target=fetch, args=(1,))
t.start(); t.join()
print(t.result)      # ❌ 报错，标准 Thread 根本没这属性
```

`target` 函数的 `return` 被**直接丢弃**。要拿结果，得准备容器让线程往里塞：

```python
results = []
def worker(i):
    results.append(fetch(i))        # 往共享列表里塞
```

### 坑 2：共享变量会"丢数"

`counter += 1` 看着一步，实际**三步**：`读 → 加 → 写回`。
两个线程可能同时读到 5，各自加 1 写回 6 —— 加了两次只涨 1。

**解法：`with lock:`**

```python
lock = threading.Lock()

def increase():
    for _ in range(TIMES):
        with lock:              # 进来锁门，出去开锁
            counter += 1        # 期间别人在门外等
```

- 等价于 `acquire()` + `try/finally: release()`
- 和文件那关的 `with open(...)` **是同一个协议**（`__enter__`/`__exit__`）
- 代价：加锁 = 排队 = 变慢。只锁真正需要保护的几行

**竞态条件最可怕的地方：它偶发。** 可能跑一万次都没事，到生产环境第一次就崩，本地还复现不出来。

## 七、第 1 关用户提问（概念澄清）

1. **"IO 密集"没懂** → IO = Input/Output，指等外部响应；外卖 vs 做饭类比
2. **`Thread(target=..., args=...)` 语法怎么来的** → 就是**普通类实例化**，跟写 `Expense(amount=..., category=...)` 一模一样；`target` 传的是**函数对象本身**（不加括号）。可以去终端敲 `help(threading.Thread)` 查。
3. **那段 for 循环没懂** → 展开成手写三遍就明白了；「列表 + 循环」是批量管理同类对象的标准模式
4. **`def run_two_serial(func)` 里 func 的意义** → 让同一个函数体能测不同任务，就是 Lambda 那关学的**高阶函数**。记忆点：`func` = 等会儿执行，`func()` = 现在就执行
5. **`lambda x=i: ...` 没懂** → 三层拆解：匿名函数 / 为什么有 x / `x=i` 是默认参数拍快照

6. **`threads` 是什么** → 就是普通列表装 Thread 对象（用户自己起的 `list_of_threads` 名字更好）
7. **`with lock:` 是什么意思** → 等价于 acquire + try/finally: release，复用上下文管理器协议
8. **列表推导式 `[Thread(...) for _ in range(10)]`** → 就是循环 append 的简写，`_` 表示"这个循环变量用不上"

# 第二部分：多进程（第 2 关）

## 一、它存在的唯一理由

第 1 关的结论逼出了第 2 关：**GIL 挡算不挡等**。CPU 密集用线程救不了（0.29 → 0.29）。

> **既然一支笔不够用，那就再开一个办公室。**

## 二、进程 vs 线程：一句话记住区别

| | 线程 | 进程 |
|---|---|---|
| 本质 | 同一间办公室的员工 | **独立的办公室** |
| GIL | 共享同一支笔 | **各有一支笔** |
| 内存 | **共享**（危险 → 要锁） | **隔离**（安全 → 不需要锁） |
| 开销 | 小 | **大**（要给新办公室配全套家具） |
| 适合 | IO 密集 | **CPU 密集** |

**进程用「内存隔离」换来了「真并行」。** 隔离是好事（不用锁），也是麻烦（数据传不过去）。

## 三、好消息：API 完全对称

```python
threading.Thread(target=f, args=(...))            # 第 1 关
multiprocessing.Process(target=f, args=(...))     # 第 2 关
```

**只换一个名字，其它一个字都不用改。** 造 / start / join、"先全 start 再全 join"、`target` 不加括号、`args` 传元组——全部照搬。

## 四、坏消息 1：Windows 必须加"保单"

Windows 用 **spawn** 启动进程：**新进程会重新导入你的模块**。

```python
# ❌ 无限套娃，直到电脑卡死
p = Process(target=work)
p.start()      # 导入时又跑到这行 → 又开一个进程 → ...

# ✅ 保单
if __name__ == "__main__":
    p = Process(target=work)
    p.start()
    p.join()
```

> 模块那关学的 `__name__ == "__main__"`，当时只是"防止 import 时跑测试"，**现在它救你的命**。
> （Linux/Mac 用 fork，没这问题；但为了可移植，一律加。）

## 五、坏消息 2：内存隔离 —— 第 2 关的灵魂

**进程 = 一个正在运行的程序 + 操作系统给它的独立内存空间。**

子进程启动时**按同一张图纸新配了一套内存**：

```python
shared_list = []      # 两栋房子各按图纸配了一台冰箱
```

子进程 append 改的是**它自己那台冰箱**，主进程那台从头到尾没被碰过。

实测结果：

```
线程版 length: 3    ← 同一栋房子，共用一台冰箱
进程版 length: 0    ← 两栋房子，各有一台
```

**隔离的代价是不能共享变量，隔离的补偿是不需要锁。**

## 六、Queue：唯一一扇能穿过隔离墙的门

**靠操作系统，而且数据是「复制运输」过去的，不是共享的。**

`q = Queue()` 装的是**一条操作系统级的管道**（不是 Python 内存）。操作系统的资源**可以被多个进程访问**——这是唯一的例外。

```
子进程 q.put(25) → 序列化(pickle)成字节 → 走操作系统管道 → 主进程反序列化 → 拿到新对象
```

**"传送带 + 编号卡"模型：**
- `q = Queue()` = 物业在楼下装了条传送带，给你一张**编号卡**
- `args=(q, i)` = 把编号卡**复印一份**交给新房子
- 子进程拿着卡，连上**同一条**传送带，把结果放上去

**为什么必须用 `args` 传 `q`？** 子进程是"新开的房子"，执行 `square_to_queue(q, i)` 时 **`q` 在它的内存里根本不存在**——只能靠 `args` 递过去。

| 东西 | 能跨进程共享吗 |
|---|---|
| 普通变量（list / dict / int） | ❌ 各有一份副本 |
| Queue / Pipe / Lock | ✅ **背后是操作系统资源** |

顺带解释：**传的东西必须能 pickle**（lambda、文件对象、数据库连接传不过去）、**传大数据会慢**（要打包拆包）。

## 七、Pool：批量任务的正规军

```python
with Pool(4) as pool:
    results = pool.map(cube, [1, 2, 3, 4, 5])     # → [1, 8, 27, 64, 125]
```

- 长得像内置 `map`，但是**真并行**
- **直接返回结果列表** —— 第 1 关「返回值拿不到」的痛点，它顺手解决了
- `with` 用完自动关池子（又见上下文管理器协议）

## 八、并行有"起步价"（第 2 关实测，重要工程直觉）

| 任务规模 | 4 个串行 | 4 个进程 | 加速比 |
|---|---|---|---|
| 小任务（~0.05 秒/个） | 0.19 秒 | 0.15 秒 | **1.27x** |
| 大任务（~0.5 秒/个） | 1.91 秒 | 0.59 秒 | **3.25x** |

（理论上限 4.00x；本机 20 核）

**为什么小任务几乎白干？** 启动一个进程要付"开办公室"的钱 —— 约 **0.1 秒/个**（重新初始化解释器 + 导入模块）。

- 小任务：任务本身才 0.05 秒，启动就要 0.1 秒 → **开销比任务还贵**
- 大任务：任务 0.5 秒，启动 0.1 秒 → 开销只占两成 → 逼近上限

> **记住这个工程直觉：并行不是免费的。任务太短，开进程反而亏本。**

2. 缩进有 2 空格的地方（`thread_version` 循环体内），跑 `black` 会统一

## 十、第 2 关用户提问（概念澄清）

1. **"进程改了 shared_list 主进程看不见"不懂** → 进程 = 独立内存空间；spawn 会重新导入模块，子进程按图纸新配一套内存；"两栋房子各有一台冰箱"
2. **"不能共享变量，Queue 怎么实现的"不懂** → 操作系统管道 + 序列化传输；数据是**复制品**不是共享；"传送带 + 编号卡"
3. **`q = Queue()` 的意义、`args=(q, i)` 里为什么传 q** → 子进程内存里没有 `q`，只能靠 args 递；传过去的是"能连上管道的凭证"，管道本身（操作系统资源）才是共享的

- **第 1 关**：线程让"等待"重叠起来，但 GIL 让"计算"无法并行 —— **线程是给 IO 密集准备的**；共享数据必须上锁，哪怕它现在看起来没事。
